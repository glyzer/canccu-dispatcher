## P1. Two-PR issues and follow-up prompts

- #86: a merged PR that leaves its issue open raises a needs-you and releases the unit.
- #87: contract-first PRs for single issues; a PR that names no issue is never merged automatically.
- #98: a contract PR that GitHub links as closing its issue goes back to the worker before any review.
- #88: a fixed safety block first in every fresh follow-up prompt; long findings by file path.
- Done when a single-issue contract PR runs end to end in a test.

## E1. Engine and config basics

- #84 `REVIEW_EFFORT_MAX`.
- #65 config and rules are read again at the start of a pass when their modification time
  changed; `STEP_BUDGET` holds new starts only, never the review, fix-check or merge of an open PR.
- #64 a usage reading older than 6 hours, or older than the dispatcher's start, counts as unknown.
- #93 one retry for a reviewer that wrote no review file.

- May run as two packages if it is over the size limit: (#84, #65, #64, #101) and (#93, #94, #69).

## C1. Config command

- `canccu-dispatcher config show [--origin]`: every setting with its value, its default and where
  the value comes from (default, host profile, global config, project config, project rules).
- `canccu-dispatcher config set KEY=VALUE [--why <text>]`: checks the key, type and range, writes
  only the override, and keeps a dated history line. It applies at the next pass (#65).
- `canccu-dispatcher config unset KEY` removes the override, with the same checks and history.
- Tokens and other secrets are never shown or set through it. Locked keys (contracts §5) are
  refused when the caller is the leader or a run; until S2 the refusal is by an environment
  marker. From C1 the dispatcher exports it into every run and answerer it starts; the leader kit
  (L1) sets it for the leader. The docs say that this is not yet a security boundary.
- It is the single write path for the Settings view of 0.3.

## M1. Keeping PRs mergeable

- #89 a waiting PR that conflicts with main gets the scripted merge of main.
- #90 the merge queue's removal reason is read; no blind retry on failed checks.
- #91 a push after a passed review gets a fix-check of the change since the last full review; a
  full review above `FIXCHECK_FULL_LINES` or on gated and risky paths (rule 2).
- #92 `KEEP_ACCEPT_ON_MAIN_MERGE`, default 0 (rule 3).
- "A merge of main only" has one meaning in #89, #91 and #92: the new head is a merge commit whose
  first parent is the reviewed (or accepted) head, whose second parent is on main, and whose tree
  equals the tree git gives for merging those two without a conflict. The dispatcher checks it by
  doing that merge again in a scratch worktree. Such a head needs no new review.
- Any other new head is the worker's change: the fix-check reads the diff from the reviewed head
  to the new head, and what came from main in it only as far as a conflict was resolved by hand.
- #21, rewritten to what is left of it: rerun the failed CI jobs once per head before any AI fix
  run, and name the failed check in the needs-you.

## R1. Nothing lost, nothing silent

- A run that ends with permission denials and a PR: compare the worktree's HEAD and `git status`
  with the PR head; a mismatch is a needs-you that lists the denials.
- The exit kind comes from the run's result; denials are attached as information.
- `CRASH_RETRY`: a crash or a killed window gets one fresh run with the handoff, then needs-you.
- `DISK_MIN_MB`. On a GitHub rate limit, passes pause until the reset and the status says so.
- A phase `starting` is written before the engine call, so a kill in between loses no result.
- `canccu-stop --forget <n>`: stop, clean up and release a unit, instead of moving state files.
- All log times in UTC with a `Z`.
- A state format version, a migration step at start, and a test that upgrades with units in flight.
- Tests for past incidents that still have none.

## N1. Asks the product owner can act on

- The classes (contracts §2) on every event.
- User-visible PRs need a section "What you will see" with before and after captures made by

  back to the worker, not to the product owner. The reviewer checks that the captures match the diff.
- `docs/security.md`: "pings carry no content" is replaced by the untrusted-content rules of

- Leader away: contracts §1, line 7.

## S1. Security, first half

- A project refuses to start runs on the default gh login unless `ALLOW_DEFAULT_GH_LOGIN=1`;
  `doctor` and `canccu-init` print the steps for the narrow token.
- Issue titles are stripped of control characters before they reach a terminal pane.
- `docs/security.md` is corrected: a Read/Edit deny rule does not protect the reviewer token from
  a subprocess.

## S2. Security, second half

- Runs, and the leader, execute as a second Unix user that cannot read the dispatcher's home
  (reviewer token, notifier token, state). The installer sets it up; `doctor` checks it. This is
  the hardened level; the simple level stays supported.
- `ACCEPT_CHANNELS`, with a stated strength per channel. At the hardened level, gated and
  high-risk PRs need an accept from a channel no AI session can write: `canccu-ship` run by the
  product owner's user (it writes an accept record with the head sha), or the label once the AI
  sessions no longer hold the product owner's login.
- A comment by the project login counts as "the product owner answered" only when no run of that
  unit was alive when it was posted.
- Only after S2 may the docs describe `KEEP_ACCEPT_ON_MAIN_MERGE=1` and
  `LEADER_ACCEPTS_HIGH_RISK=1`.

## L1. Leader tools, kit and measurement

- `canccu-dispatcher leader brief`: the live state, the leader's open feed lines and the next
  steps, so a fresh leader session needs no handover reading.
- The actions log (contracts §7); `canccu-ship` checks the owner and `LEADER_ACCEPTS`.
- The kit: `templates/leader/CLAUDE.md` (the role, what it may accept, what always goes to the
  product owner, its commands, how it waits on the feed, the ask form) and a permissions file (no
  reviewer token, no force-push, no direct merge). `canccu-init --leader <project>` writes both
  and sets `LEADER=on`.
- The rename: `docs/reference/lead.md` becomes `leader.md`; the pane title in `canccu-up`; every
  user-facing "lead" that means the role. `lead_of` in code stays.
- Measurement: leader tokens per project; the duration of each worker's full local test run;
  messages to the product owner per channel and class.

## T1. Release gate tests

- A scenario suite against a real sandbox repo with a fake engine (no model tokens): single
  issue, package, contract-first pair, conflict while waiting, merge-queue removal, push after a
  pass, denied push, crash.
- It runs before every tag; a red scenario blocks the tag.

## Building the dispatcher with itself

- The host that builds 0.2 runs a tagged build, not main. It moves to a new build only between
  packages, after `canccu-dispatch --dry-run` of the new build on the live state shows no surprise.
- Rollback with units in flight is written down and tested once.
- Bug issues carry `Regression of: #<pr>`; the reviewer asks for it on a fix PR.

## Release step

1. `--version` prints the snapshot id, not only `VERSION`.
2. Tag `v0.2.0` with a changelog built from the merged PR titles.
3. The tag runs for one day with real work on the building host, then other hosts install it.
4. After 5 to 7 days and at least 50 merged issues, the targets are measured again. A miss
   becomes an issue in 0.3.
